01Summary

DormDash is a Next.js application deployed to Vercel through GitHub Actions. The stack is deliberately small: one framework, one styling engine, one authentication provider, and one hosting platform. Everything is written in TypeScript and validated on every pull request before it can reach main.

Application

Next.js 16 App Router with React 19 server and client components, compiled by Turbopack.

Interface

Tailwind CSS v4 with a custom light/dark theme, responsive layouts, and a mobile bottom tab bar.

Identity

Clerk handles sign-in, sign-up, sessions, OAuth, and MFA. Protected routes call auth.protect().

Delivery

GitHub Actions runs CI and deploys to Vercel preview (test) and production environments.

03Authentication and security

TechnologyVersionRole
Clerk 7.9.23 Hosted identity provider: email + password, Google OAuth, session cookies, and multi-factor authentication.
Clerk middleware clerkMiddleware() Runs in src/proxy.ts, protects the session context, and injects a per-request Content-Security-Policy nonce.
Route-level authorisation auth.protect() Each protected page calls await auth.protect() on the server. Unauthenticated visitors are redirected to sign-in with a return URL.
Content Security Policy nonce-based Restricts scripts, styles, fonts, images, and frames to known origins, including the Clerk Frontend API and Turnstile challenge endpoints.
HTTP security headers next.config.ts X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy disabling camera, microphone, geolocation and browsing topics, Strict-Transport-Security for two years with preload.
Secret management — Clerk keys live in .env.local (gitignored), Vercel environment variables, and GitHub Actions secrets. No keys are committed; git history was scanned before the repo was made public.
Defence in depth. Authorisation is enforced per route on the server, not by hiding UI. The middleware handles session context and CSP; the page itself re-checks the session with auth.protect(), so a new route is safe by default the moment it opts in.

Deployment flows

WorkflowTriggerWhat it does
CI Push to main / test, all pull requests Install with npm ci, lint, typecheck, unit tests, production build, audit.
Deploy to Test Push to test, or manual Pull the Vercel preview environment, build, deploy a preview, then HTTP smoke test the URL.
Deploy to Production Manual only (workflow_dispatch) Pull the production environment, build, deploy with --prod, then smoke test.
CodeQL Push, pull request, weekly schedule Static security analysis and upload of results to code scanning.
Production is a deliberate human decision. Merging to main runs CI but does not ship. A release is started from Actions → Deploy to Production → Run workflow. This works on every GitHub plan, including the free tier where required reviewers are unavailable on private repositories.

Branch protection and environments

  • Ruleset protect-main on main: no deletion, no force-push, required status check, and the branch must be up to date before merging.
  • GitHub environments test and production record deployment history and expose a deployment URL.
  • Deploy jobs self-skip with a notice if VERCEL_TOKEN, VERCEL_ORG_ID, or VERCEL_PROJECT_ID are missing, so CI never fails for lack of hosting credentials.
  • Vercel Deployment Protection is disabled so the pipeline's smoke tests and the public site are reachable; Clerk still guards every private route.

09Current status and known gaps

Working end to end

✓ Login and protected routes
✓ Responsive mobile UI and PWA manifest
✓ CI on every pull request
✓ Test and production deploys with smoke tests
✓ Manual release gate and branch protection

Not yet in place

Database — PostgreSQL and Prisma are planned but not wired up.
Clerk production keys — the live site still runs development keys.
PNG icons — an SVG icon exists; iOS needs 192/512 PNG and an apple-touch-icon.
Input validation — Zod is intended for server-side schema validation.

Upgrade policy. Next.js, React, TypeScript, and ESLint majors are treated as planned migrations rather than automatic pull requests. Dependabot is configured to raise only minor and patch updates for them, because a major bump can break typescript-eslint or eslint-config-next before those tools catch up.
